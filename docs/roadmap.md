# Room Finder MVP Roadmap

このロードマップは、`SPEC.md` に定義したMVPを、責務が重ならずコンフリクトしにくいIssue単位へ分割したものである。

Issue作成時は、各項目を1 Issue・1 `issue/{issue_number}` ブランチ・1 Pull Requestとして扱う。

## 実装順序

```text
1. プロジェクト基盤
   ↓
2. DB・マイグレーション
   ↓
3. Go APIの保存契約
   ├── 4. 検索プロファイルAPI
   └── 5. 物件保存API
          ↓
6. LIFULL HOME'S取得・抽出
          ↓
7. Agent判定・再試行ランナー
          ↓
8. 最小Web表示
```

## Issue候補

### Issue 1: プロジェクト基盤をbuildlog準拠で作成する

- 優先度: P0
- 依存: なし
- 対象: `web/`, `api/`, `sql/`, `compose.yml`, CI設定の最小構成
- 完了条件:
  - SvelteKit / Go / Docker Compose / Atlasのローカル開発手順が動作する
  - buildlogと同じディレクトリ責務・検証コマンドを用意する
  - WebとAPIの疎通確認ができる
- コンフリクト回避: 基盤ファイルのみを変更し、業務モデルや画面機能を含めない

### Issue 2: 検索プロファイルと物件のDBスキーマを追加する

- 優先度: P0
- 依存: Issue 1
- 対象: `sql/migrations/`, DB entity定義
- 完了条件:
  - プロファイルID、初回プロンプト、解釈済み必須条件を保存できる
  - 条件一致物件の現在情報を保存できる
  - プロファイルの作成後変更不可を表現できる
  - Atlasの検証が通る
- コンフリクト回避: DBとentityだけを変更し、API handlerやCrawlerを含めない

### Issue 3: 構造化データを受け付けるGo API契約を実装する

- 優先度: P0
- 依存: Issue 2
- 対象: `api/handler/`, `api/service/`, `api/repository/`, `api/entity/`
- 完了条件:
  - プロファイル作成APIが動作する
  - Agentから物件情報を受け付ける保存APIが動作する
  - 必須項目・データ型・URL・プロファイルIDを検証する
  - APIがDBへ保存し、DB接続情報をクライアントへ公開しない
- コンフリクト回避: APIの保存契約を先に固定し、CrawlerやAgent実装を含めない

### Issue 4: 検索プロファイルの不変性を実装する

- 優先度: P0
- 依存: Issue 3
- 対象: プロファイルAPI・service・テスト
- 完了条件:
  - プロファイルを新規作成できる
  - 作成済みプロファイルを更新できない
  - 条件を変える場合は新しいプロファイルを作成する
  - 無効化・削除の扱いが既存ルールに従う
- コンフリクト回避: プロファイル領域だけを変更し、物件取得処理を変更しない

### Issue 5: LIFULL HOME'Sの取得アダプターを実装する

- 優先度: P0
- 依存: Issue 3
- 対象: ローカルCrawler、LIFULL HOME'S専用取得処理
- 完了条件:
  - 指定された検索プロファイルに基づき検索結果を取得できる
  - 物件詳細から取得可能な現在情報を抽出できる
  - 取得元URLと取得日時を保持できる
  - 利用規約・robots.txt・アクセス頻度を確認した実装になっている
- コンフリクト回避: LIFULL HOME'S専用ディレクトリに閉じ込め、Go APIの共通契約以外を変更しない

### Issue 6: Agentによる構造化抽出・必須条件判定を実装する

- 優先度: P0
- 依存: Issue 3、Issue 5
- 対象: ローカルAgent、OpenAI API連携、構造化出力スキーマ
- 完了条件:
  - 初回プロンプトから必須条件を抽出できる
  - 物件情報を定義済みスキーマで返せる
  - 各項目の根拠を返せる
  - 情報を推測で補完しない
  - すべての必須条件を満たす物件だけを保存APIへ送る
- コンフリクト回避: Agent・プロンプト・スキーマだけを変更し、APIの保存処理を変更しない

### Issue 7: 日次実行・再試行・冪等性を実装する

- 優先度: P0
- 依存: Issue 4、Issue 5、Issue 6
- 対象: ローカルランナー、実行状態、リトライ、保存APIの冪等性
- 完了条件:
  - 保存済みプロファイルを毎日実行できる
  - 一時的な通信エラー・タイムアウト・形式不正を再試行できる
  - 実行単位の再試行上限を設定できる
  - 未完了データを次回実行へ持ち越せる
  - 同じ物件を再送しても重複登録されない
- コンフリクト回避: 実行制御に集中し、サイト別抽出ロジックを変更しない

### Issue 8: 条件一致物件を表示する最小Web画面を実装する

- 優先度: P1
- 依存: Issue 3、Issue 4、Issue 7
- 対象: `web/`
- 完了条件:
  - プロファイル一覧を確認できる
  - 条件一致物件を確認できる
  - 物件詳細と取得元URLを確認できる
  - WebからDBへ直接接続せず、Go API経由で取得する
- コンフリクト回避: API契約を変更せず、既存のbuildlogのSvelteKit実装パターンを踏襲する

## 後続Issue

以下はMVP後に分離する。

- 2サイト目以降の追加
- 掲載履歴・家賃変更履歴
- お気に入り・除外
- ランキング・優先度付け
- ユーザーの反応からの好みの学習
- 通知
- ユーザーアカウント・権限管理
- Cloudflare Pages / Cloud Run / Neon / Secret Manager / WIFの本番デプロイ

## 分割方針

- DB、API契約、サイト取得、Agent、実行制御、UIの責務を分ける
- 同じファイル群を複数Issueで同時に変更しない
- 後続Issueは先行IssueのAPI・DB契約を利用するだけにする
- 複数サイト対応は、LIFULL HOME'S実装が安定してから別Issueにする
- 大きな共通化は、2サイト目が必要になった時点で別Issueとして検討する
